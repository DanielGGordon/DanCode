## [2026-05-15 22:46] Phase 1: Shellhost MVP + web wiring

Playwright starts every `webServer` entry BEFORE running `globalSetup`, so spawning a UNIX-socket dependency in globalSetup can't satisfy a server that polls for it during webServer boot — the fix is to spawn the dependency inside the webServer entry's process (a small wrapper script that boots the child and then loads the server inline). Isolating shellhost-backed E2E behind a per-run temp `HOME` is much simpler than threading data-dir env vars through auth/projects/terminal modules, and keeps real `~/.dancode` credentials out of the test path. Port 3002 is grabbed by Tailscale's `serve` on the dev Pi; check `tailscale serve status` before picking E2E ports. The legacy `TerminalManager._publicMeta` (added by Phase 4) silently dropped `lastActivity` and broke the existing creation-time assertion — small alignment with `get()`/`list()` is the right fix until Phase 3/9 rewrites that path. Phase 1 also exposes a server-side ring buffer that duplicates Phase 2's planned disk-backed scrollback — drop it when Phase 2 lands.

## [2026-05-15 23:25] Phase 2: Disk-persisted scrollback

xterm's default 1000-line scrollback silently truncates a 50KB disk replay to ~2KB; the disk write-through path can be byte-perfect while the browser-visible scrollback looks broken — bump xterm's `scrollback` option whenever the replay budget exceeds what 1000 lines can hold. PTYs run in cooked mode by default and the TTY layer expands `\n` → `\r\n` before output reaches scrollback, so 120KB of `yes` input lands as ~180KB on disk and a 50KB tail contains only ~17K 'y' characters — count bytes, not visible glyphs, when asserting replay size. Shell-typed sentinels are echoed back as input, so detecting "command complete" by substring match on the sentinel literal fires on the echo first; either build the sentinel via shell concatenation (`S=__SCROLL; S="${S}_END__"`) or detect by byte count. `e2e-helpers.login` was reading credentials from the real `homedir()` even when the server ran under `DANCODE_E2E_HOME`, which only manifests once a second shellhost-E2E spec is added — first spec sets up account, second spec fails 401. Parallel Playwright workers race POST /api/auth/setup against the same temp HOME; the loser can't read the matching TOTP secret, so shellhost E2Es must run with `workers: 1`. Holding an open fd per terminal and calling `writeSync` is the right write-through primitive — `fs.appendFileSync` would reopen the file on every chunk. The `attach` op idempotency on the same connection naturally prevents duplicate replays on reconnect; the deeper invariant is that scrollback removal on `kill` must wipe `<baseDir>/<id>/` entirely (which will collide with Phase 3+ metadata files unless coordinated).

## [2026-05-16 00:30] Phase 3: Survive web-server restart

The previous attempt timed out after 60 minutes but actually committed working code (commit `2b8dc34`) before going on an unrelated tangent (adding TOTP `epochTolerance` to `auth.js`). Rescue verified all 7 vitest cases and 3 shellhost E2E specs are green; reverted the auth.js tangent since the restart spec bypasses TOTP via in-process `createSession()`. The boot-stack supervises the dancode-server as a child process (not inline) so `process.exit(0)` from the `/api/test-only/kill-server` handler kills only the server, freeing the port for an immediate respawn; running the server inline would have killed the supervisor with it. The Socket.IO terminal namespace had to switch from a captured `manager` reference to a lazy `resolve()` getter — module-level `terminalManager` is reassigned on each `startServer()` call, and connections opened against the OLD manager (closed) would otherwise route writes into the void after an in-process restart. `recover()` calls `attach` per-recovered terminal so live `output` events route through the fresh manager, but it must tolerate `attach` failing silently (`try { await this.client.attach(...) } catch {}`) since shellhost considers attach idempotent on the same client connection. The 1MB stress test must NOT use a shell-echoed sentinel as the completion signal — the shell echoes the command back before the heavy generator finishes, so detect completion by counting bytes on disk via `waitFor(() => count >= 1_000_000)` instead. The test-only kill endpoint must be allowlisted in `requireAuth` AND guarded inside its handler by `NODE_ENV=test`; either gate alone leaves a hole.

## [2026-05-16 01:12] Phase 4: Layout persistence + project restore

Per-slug in-process write lock combined with `open()→writeFile→fsync→rename` is the simplest way to satisfy "20 parallel PUTs, never a torn file" — the rename is atomic per filesystem, and the lock guarantees the final winner identity is one of the inputs. The acceptance bar didn't require multi-process safety, and a single-process lock is dramatically less code than file-locks or O_EXCL dance. The `runPwdInPane` helper bit me on xterm column-width line wrapping: a 54-char `/tmp/...` path printed via `printf` reflowed mid-string in a half-viewport pane, and the parser was picking only the first wrapped row — joining all non-empty rows between the two sentinels (instead of `lines[0]`) is the robust fix that future phases doing similar shell-output capture should adopt. Project rename safety hinges on operation order: write new config → move layout dir → remove old config (a crash mid-rename then leaves the new state intact rather than orphaning data). The acceptance spec's "GET returns saved layout or default" plus the missing-file-warning flow led to annotating GET responses with a `missingFiles: []` field rather than scrubbing absent paths from `openFiles` — the client decides what to render, so the server should return everything plus metadata. `POST /api/terminals` accepts absolute cwds without containment validation (relative cwds are validated to stay in the project), which the layout-restore E2E exploits to spawn two terminals with distinct cwds; Phase 8/10 may want to tighten this. The `_publicMeta` of both terminal managers was missing `cwd`/`command`, which the client needed to persist into layout.json — symmetric extension to both (`ShellhostTerminalManager` and legacy `TerminalManager`) keeps the two backends interchangeable until Phase 9 removes tmux. Playwright shellhost E2Es flaked on first run (401 on a fresh temp HOME, then passed on retry), suggesting a setup-vs-server-boot race in `boot-stack.mjs` that future phases relying on `login()` should be aware of — a single retry around the initial `login()` call would harden it.

## [2026-05-16 01:42] Phase 5: Pi-reboot recovery (respawn with scrollback banner)

The `dancode-shellhost` socket-level client emits an `'error'` event on the EventEmitter when the underlying UNIX socket sees ECONNRESET — which fires whenever shellhost dies via SIGKILL. Without a registered `'error'` listener Node rethrows and crashes the server, which manifests as a 500 ("shellhost connection closed") on the next reconnect rather than what you'd guess (a hang or a clean 200). `ShellhostTerminalManager._wireEvents()` now attaches `error` + `close` listeners; future generators that create clients to shellhost (Phase 7+ for Claude session detection, Phase 8 background mode) must do the same. Polling the socket file alone is not a reliable "shellhost is back up" check after SIGKILL because the boot-stack races to unlink + spawn while we're polling — the more robust signal is to wait for the pidfile to flip to a NEW pid (proving the supervisor's exit handler ran) and only then poll the socket. The respawn op persists the banner into the same `scrollback.log` BEFORE notifying live attached listeners, which means later attaches see "prior content + banner + new live output" via the existing `getScrollback` replay; there's no separate replay-then-banner sequence for attached listeners and no client-side ordering work needed. Boot-stack now auto-respawns shellhost on exit (mirrors the existing server respawn) and explicitly unlinks the stale socket before spawning the replacement — without the unlink, the new shellhost's `bind()` fails with EADDRINUSE. The `setInterval` for periodic `lastActiveAt` persistence had to be `unref()`'d, else vitest hangs on shutdown waiting for the timer to drain; `vi.useFakeTimers({ now: ... })` only mocks timer callbacks AND `Date.now` if you pass an explicit `now` (default behavior leaves Date alone). Server-side respawn lives on the layout-GET endpoint and as a backstop in the Socket.IO terminal-namespace connect handler — the dual hook is on purpose because parallel page-load fetches race the `/api/projects/X/layout` and the WebSocket attach, and you don't want the attach to find a still-orphan entry.
